# AppDB 42981 (Dorico 6.x) — issue analysis and patch plan

User criterion 4: fix the four issues reported on
<https://appdb.winehq.org/objectManager.php?sClass=version&iId=42981>.

## Reported symptoms (verbatim, AppDB test 117653, Lorelei, 2026-08-02, Wine 11.13, Nobara)

1. "Sometimes dropdowns may just show a white box, usually closing and re-opening fixes this."
2. "When I make a new project I can add parts and notes but i cant play them back. There is no
   sound, and if I go to the 'play' tab it just locks up." (workaround used: copy an old project)
3. "Sometimes dialogs get stuck, like the browser to open a file, or settings menus. Just hit
   escape/close the dialog window, and reopen it and usually then it works fine"
4. "I get an error when I close dorico, I just dismiss it"

Reporter environment: `WINEARCH=win64`, `winecfg /v win10`, winetricks
`corefonts vcrun2019 dotnet48 dxvk webview2`, `HKCU\Software\Wine\Drivers Default_Rate=48000`,
and the PipeWire workaround `pw-metadata -n settings 0 clock.force-quantum 1024`.

**Dorico is not SDA.** Dorico 6 is a native Win32 **Qt 6** application (Steinberg's own dev blog:
its main desktop notation apps are built on Qt) whose audio engine/VST hosting/ASIO layer is shared
with Cubase/Nuendo. Nothing in this project's JavaFX/Glass analysis applies to it.

## Per-symptom analysis

| # | most likely subsystem | Wine source location | candidate patch | confidence |
|---|---|---|---|---|
| 1 white-box dropdowns | layered/popup windows not composited when a D3D/GL client child window targets them (WineHQ **60173**; related 50495, 60047, 50595/50743/37876, and Qt-specific 60259; Qt6+D3D11 present bug **60366**) | `dlls/winex11.drv/init.c: needs_offscreen_rendering()` (~line 223); mirror `dlls/winewayland.drv/window.c` | make `WS_EX_LAYERED`/`data->layered` windows take the offscreen/XComposite path; **or** the wine-staging `dcomp-DCompositionCreateDevice2` set (already staged in `csp-wine/patches/local/dcomp-staging/`, whose definition says it "Fixes 58315 Clip Studio Paint 4 menus turn black when clicked") if tracing shows `DCompositionCreateDevice` is called | medium |
| 2 dialogs get stuck | stale client-surface toplevel on dialog creation/reparent (WineHQ **60179**), a regression from commit `695e721719e761023018a90a0f0828a566bd676b` "win32u: Keep track of client surface toplevel window" (11.13) | `dlls/win32u/window.c` (`client_surface_update_locked` ~361, `update_client_surfaces` ~379, `NtUserSetParent` ~700-800, `NtUserCreateWindowEx` ~5880-6190), `include/wine/gdi_driver.h: struct client_surface` | invert the toplevel caching for the present path | medium |
| 3 no sound / Play tab locks up | `advapi32` wait-chain API still stubbed (WineHQ **53746**); plus no ASIO implementation in Wine (bug 51088) | `dlls/advapi32/advapi.c` (~302-315), `dlls/advapi32/advapi32.spec` (104, 373, 551) | implement `OpenThreadWaitChainSession`/`GetThreadWaitChain` | low-medium |
| 4 error on close | **not determinable** without running Dorico 6 and capturing the failing call | — | — | none |

Setup-only levers worth testing before patching: do not enable "Emulate a virtual desktop"
(precondition for Qt popup bugs 59338/60259); `HKCU\Software\Wine\X11 Driver` →
`GrabFullscreen=N`, `GrabPointer=N`; prefer a native X11 session over XWayland while focus bugs
59345/59610 are open; keep DXVK only if bug 60366 (Qt6 present) is the actual problem — DXVK
shadows a patched `dxgi`/`dcomp`, which is fatal for the dcomp route.
Note: Wine 11.18's tree contains **no** reader for `HKCU\Software\Wine\Drivers\Default_Rate`
(tree-wide grep is empty), so that guide step is a no-op on this version.

## Prerequisite / honest limit

Reproducing any of this requires a **Dorico 6 installation** (free Dorico SE is sufficient per the
AppDB workaround) plus a Steinberg account for licensing. That media is not present on this host and
is not redistributable. Therefore:

* symptoms 1-3 are mapped to concrete Wine defects with existing patch material, but **none has
  been reproduced or verified here**;
* symptom 4 cannot be attributed at all without a run;
* no patch in `patches/local/` claims to fix these issues, and none will until it is verified.

The natural way to unblock is to let this project's SDA port reach a working login/download state
(it is the tool that installs Dorico), then install Dorico SE through it and reproduce.
