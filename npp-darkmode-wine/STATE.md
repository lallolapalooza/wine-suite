## ROOT CAUSE (evidence-backed)
- NPP darkens the menu bar ONLY via the undocumented UAH protocol:
  wndproc subclass handles WM_UAHDRAWMENU (0x0091) / WM_UAHDRAWMENUITEM (0x0092)
  (src/NppDarkMode.cpp:4154-4210, UAHMenuBar.h; structs UAHMENU/UAHDRAWMENUITEM/
   UAHMENUITEM/UAHMENUITEMMETRICS).
- NPP enables it via uxtheme ordinals: 133 AllowDarkModeForWindow,
  135 SetPreferredAppMode (>=18362), 136 FlushMenuThemes, 137 IsDarkModeAllowedForWindow,
  104 RefreshImmersiveColorPolicyState, 49 OpenNcThemeData  (src/DarkMode.cpp:284-333).
  `AllowDarkModeForApp(allow)` -> SetPreferredAppMode(ForceDark=2) (src/DarkMode.cpp:42-75).
  `SetDarkMode()` -> AllowDarkModeForApp(useDark) + FlushMenuThemes().
- Probe under Wine 11.18: all those ordinals resolve (so NPP g_darkModeSupported=TRUE),
  BUT: AllowDarkModeForWindow -> FALSE, IsDarkModeAllowedForWindow -> FALSE,
  SetPreferredAppMode -> 0, and **zero** UAH messages ever delivered.
- Wine 11.18 source: dlls/uxtheme/system.c -> those are `FIXME("stub")`.
  dlls/win32u/menu.c has NO dark/UAH handling; include/winuser.h lacks WM_UAH*.
- Wine reports 10.0 build 19045 (passes NPP's CheckBuildNumber; >=19041 so NPP's
  setDarkTitleBar takes the DwmSetWindowAttribute path, and dark forcing comes from
  SetPreferredAppMode(ForceDark)).

## DESIGN (current)
1. win32u: new per-process dark-mode state + entry points:
   NtUserSetPreferredAppMode(int)->prev, NtUserAllowDarkModeForWindow(HWND,BOOL)->BOOL,
   NtUserIsDarkModeAllowedForWindow(HWND)->BOOL, NtUserFlushMenuThemes().
   Mode semantics: Default=0, AllowDark=1, ForceDark=2, ForceLight=3.
   Dark for window = (mode==ForceDark) || (mode==AllowDark && per-window flag).
2. uxtheme/system.c: ordinals 133/135/136/137/104 forward to the win32u functions
   (spec: wire via win32u.NtUser* forwarding).
3. win32u/menu.c NtUserDrawMenuBarTemp(): when dark allowed for hwnd ->
   send WM_UAHINITMENU (0x93); send WM_UAHDRAWMENU (0x91) with UAHMENU{hmenu,hdc,flags};
   per item send WM_UAHDRAWMENUITEM (0x92) with UAHDRAWMENUITEM{dis,um,umi};
   skip default bar background + default item drawing when app handles it.
   Also WM_UAHMEASUREMENUITEM (0x94) in calc_menu_bar_size per bar item.
   Layer sizes: UAHMENUITEMMETRICS union rgsizeBar[2]{cx,cy}/rgsizePopup[4]{cx,cy}.
4. Popups (WM_UAHNCPAINTMENUPOPUP 0x95) — phase 2 if needed.

## BUILD ARCH NOTES (learned the hard way)
- win32u is a dual module: `MODULE = win32u.dll` + `UNIXLIB = win32u.so`.
  The *real* implementations (menu.c, window.c, defwnd.c, ...) are compiled into the
  **unix** library win32u.so; the PE win32u.dll only links main.c + generated syscall
  thunks. So new win32u source files MUST carry `#pragma makedep unix`, otherwise
  makedep builds them for the PE side and they fail on wine/gdi_driver.h
  ("can only be used on the Unix side").
- New win32u source: add to SOURCES in dlls/win32u/Makefile.in AND put
  `#pragma makedep unix` at the top of the file. Include order must start with
  ntgdi_private.h (which pulls win32u_private.h) before ntuser_private.h.
- After Makefile.in changes: run ./config.status then make (make caches Makefiles).
- dlls/win32u/x86_64-windows/win32u.dll links ONLY main.o -> implementations are unix-side.
- Test harness: tools/npp_dark_test.py samples median of blank menu-bar/toolbar bands
  (x 0.60-0.90) after parking the pointer at (1500,980); stock wine correctly => BUG.

## DESIGN v2 (current, after v1 was abandoned)
v1 added 4 new win32u syscalls (darkmode.c). ABANDONED: adding win32u syscalls also
requires updating the checked-in generated table dlls/win32u/win32syscalls.h
("Automatically generated by tools/make_specfiles", 3080 SYSCALL_ENTRY lines); the PE
win32u.dll link then fails with undefined references to the new exports. All v1 changes
were reverted (files restored from patches-draft/orig; darkmode.c deleted).

v2 uses existing, documented mechanisms and needs no new syscalls:
- Per-window state in a window property `__wine_dark_mode` (1 = dark, 2 = explicitly
  light, absent = unset). Written via SetPropW (user32), read in win32u via NtUserGetProp.
- dlls/dwmapi/dwmapi_main.c: DwmSetWindowAttribute/DwmGetWindowAttribute implement
  DWMWA_USE_IMMERSIVE_DARK_MODE (=20) by setting/reading that property. Notepad++ 8.9.8.1
  uses exactly this on build >= 19041 (NppDarkMode.cpp:4236, Windows reports 19045).
- dlls/uxtheme/system.c: AllowDarkModeForWindow/IsDarkModeAllowedForWindow use the
  property; SetPreferredAppMode(ForceDark) marks existing windows of the process via
  EnumWindows; FlushMenuThemes/RefreshImmersiveColorPolicyState are no-ops.
- dlls/win32u/menu.c: is_dark_mode_allowed_for_window() = property == 1; when true,
  NtUserDrawMenuBarTemp() sends WM_UAHINITMENU + WM_UAHDRAWMENU + per-item
  WM_UAHDRAWMENUITEM and skips the default drawing.
Patch set: 3 patches (menu.c, system.c, dwmapi_main.c). No app-exclusive patches.
NPP call chain: NppBigSwitch.cpp:228 installs the menu-bar subclass on WM_CREATE;
NppDarkMode.cpp:4236 sets the DWM attribute; 4154-4210 handles the UAH messages.
